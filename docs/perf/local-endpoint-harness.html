Method note 2026-08-28 Issue #22 PangenomeAPI

How /seqtubemap was driven on a laptop

Two isolated API instances, one on each side of the change, serving the same five regions over HTTP — so the before-and-after could be measured on the wire rather than inferred from a unit test. Then pgb's own parser was run over both sides, and it recovers bit-identical arrays. This is the method, including the one stand-in that limits what it proves.

Isolation

Production was never involved. The release branch — the one the server follows — was not read, written, or deployed to. Both instances bound to 127.0.0.1 on ports 8100 and 8101; production is :8000 on pangenome-api.ucsd.edu.

Everything the harness created lives outside the repository, except one gitignored cache/ directory that was deleted afterwards. git status is clean.

01

Why this needs a harness at all

Serving one /seqtubemap request touches four things a developer machine does not have. Docker would supply all of them at once, and docker-compose.yml exists for exactly that — but this machine has no Docker daemon, so each was supplied separately.

What the endpoint wants, and why it is missing
DependencyWhy it is missing here
The HPRC v2 .gbz graphMulti-gigabyte, not distributable; lives on the server
vg, called twicevgteam ship a Linux static build; this host is darwin/arm64
panCT + git config pathsA developer setup step, unset in this checkout
adaptagrams, ogdf-pythonCompiled inside the Docker image, not on the host

The Python test suite already solves three of these — conftest.py stubs the native libraries, finds or stubs panCT, and supplies the git config through git's environment variables. What it cannot solve is vg, which is why four tests in test_seqtubemap_endpoint.py skip on a machine without it. Those are precisely the tests that render a real tube map.

So before this harness, no part of /seqtubemap had ever run end to end on this machine. The coverage came from CI, where vg is installed, and from the Node-level tests that sit below HTTP.

02

What “isolated instance” means, precisely

Two uvicorn processes, each serving main:app out of a different checkout, both running at the same time. They share every harness piece deliberately: anything shared is a constant across the comparison, and therefore cannot contribute to the difference.

03

The trick that removes the need for graph data

This is the part worth understanding, because it is not a test hook. It is a production code path, used as intended.

main.py:735

subgraph_cached = preprocess_gfa_subgraph_w_walk.exists()

with stage_timing(stages, "subgraph_extract"):
    if not subgraph_cached:
        ...SubgraphMC(...); GenerateWalksMC(...)

If the extracted subgraph is already on disk, the endpoint skips extraction entirely — no .gbz, no gfabase, no tabix lookups. That branch exists so a repeated region is fast. It also means pre-placing a subgraph file is enough to make the rest of the pipeline run.

The path it looks for is built from the query parameters, and the five fixtures in tests/fixtures/seqtubemap/ were copied out of the production server's own cache directory under the server's own filenames. They drop straight in — and the region in each filename is the region to request.

Five committed fixtures become five servable regions

mkdir -p cache/seqtubemap/mc
cp tests/fixtures/seqtubemap/*.gfa cache/seqtubemap/mc/

The second half of the same trick is issue #19: the .walk.gz derivatives are opened the first time something reads one, rather than at import. A request with no minigraphnode reads none — so data.path can point at an empty directory and the app still boots and serves.

04

The stand-ins, and what each one costs

git config
tools.path and data.path supplied through GIT_CONFIG_COUNT / KEY_n / VALUE_n — the same mechanism conftest.py uses. Any git config --get in a child process sees them.
Cost: none. Nothing on disk changes; the developer's own config is untouched.
panCT
Cloned for real at 03c406b, the commit CI pins. The logging in the [stage-timing] line below is therefore panCT's own, not a placeholder's.
Cost: none. This is the real dependency.
adaptagrams
ogdf_python
Two stub modules on PYTHONPATH. main.py imports them at module scope through bandage_graph; they are the 3D graph layout libraries, and nothing in the /seqtubemap path calls them.
Cost: /json was non-functional in these instances. It was not exercised and no claim here covers it.
vg
A shell script first on PATH, implementing exactly the two invocations main.py makes. See below — this is the one that matters.
Cost: the GFA→JSON step is this repo's own derivation, not vg's. Detailed in section 06.

The vg stand-in

ConvertGfaToVg and ConvertVgToJson each run subprocess.run against vg unconditionally — there is no “skip if the output exists” branch to exploit, the way there is for extraction. Without a vg on PATH, a request cannot get past gfa_to_vg.

$S/bin/vg — deliberately outside the repository

case "${1:-}" in
  convert)   # vg convert -g <in.gfa>  -> stdout   (main.py:464)
    printf 'GFA_SHIM\t%s\n' "$(cd "$(dirname "$3")" && pwd)/$(basename "$3")"
    ;;
  view)      # vg view -j <in.vg>      -> stdout   (main.py:486)
    gfa=$(awk -F'\t' '/^GFA_SHIM/{print $2; exit}' "$3")
    out=$(mktemp -t vgshim); trap 'rm -f "$out"' EXIT
    node "$REPO/perf/gfa-to-vg-json.mjs" "$gfa" "$out" >/dev/null 2>&1
    cat "$out"
    ;;
  *) echo "vg shim: unsupported invocation: $*" >&2; exit 64 ;;
esac

The .vg protobuf is a private intermediate — nothing but vg view ever reads it, and the endpoint deletes it afterwards — so convert need not produce one. It writes a marker naming the GFA it was given; view reads that marker and converts the GFA directly with perf/gfa-to-vg-json.mjs.

It was verified before being trusted. Over the 90 bp fixture, the stand-in's output is identical to the committed subgraph_chr8_78771162_78771252_v2_with_walk.json — the very file the Node tests and the band-data baselines are built from. The Node stage therefore received, over HTTP, exactly the input it receives in npm test.

Why it stays out of the repo

A file named vg that silently is not vg is a hazard. It should not be findable by anyone who has not read this page, so the reproducible recipe is the only durable form it takes.

Conformance, checked on the response bodies

For all five regions the “after” body is byte-identical to the “before” body once color=, class="track{id}" and <title></title> are textually deleted from it. Drawable counts in g.track are unchanged — 592, 8,089, 13,246, 35,020, 44,795 — and the client's parsing contract passes on every one. nodewidthoption=normal, the one path whose geometry could have shifted, is identical too, with the same nine <text> elements. Neither server log holds an error, a traceback, or a non-200.

Byte reductions read ~14% here against ~16.6% measured on the fixtures, and the reason is the absence of minigraphnode: with no PCLAI scheme every coordinate attribute is the short literal None, so the removed attributes are a smaller share of a smaller document.

06

Then the client's own parser

curl stood in for pgb's fetch, not for pgb. It retrieves the bytes; it does not parse them — and parsing is where compatibility actually lives. That half was checked separately, and at first against this repository's written description of what pgb requires, which is a weaker thing than it sounds.

pgb is checked out on the same machine, so the description was replaced by the code. parseBands.ts and parseSegmentBoxes.ts were run directly over the five subgraphs as rendered by both sides. All ten documents were accepted — and more than accepted:

The roadmap calls this the strongest available assertion — run the client's own parser over before and after, and diff the recovered arrays — and it is now met with the client's code rather than a description of it.

Two things fell out of reading that parser

Our transcription was looser than the real gate. It made fill-opacity and trackName optional; pgb requires both, literally — fill-opacity: 1; is a hardcoded token inside the pattern. A lenient transcription is worse than none, because it is false assurance about somebody else's gate. It now mirrors pgb's own construction.

Filed as #52

A reversal draws shapes pgb cannot read — corners carry no trackName, are quadratics where the grammar wants cubics, and neither they nor a reversal's vertical rectangles carry the required fill-opacity. Because pgb compares drawables counted against drawables matched, one unreadable shape refuses the whole document — an error card, not a degraded picture.

Latent: no committed fixture draws a corner, and all five real subgraphs are entirely rects and curves at alpha: 1. And it predates this change in both directions. It now has a failing example in the test suite rather than a comment.

07

What this proves, and what it does not

It proves

That the post-change code serves /seqtubemap over real HTTP — real handler, real caching branch, real Node subprocess; that the documents differ from the pre-change ones by exactly the three removals; and that the saving sits where the change was made. A genuine A/B: the instances differ only in the checkout they serve. And, separately from the harness, that pgb's own parser recovers identical numbers from both sides.

It does not prove

Anything about the bytes real vg produces. That step ran through this repository's own derivation, known to differ from vg view -j in at least subrange naming. It sits upstream of the change, so it cannot mask a regression introduced here — but “production will return exactly these bytes” is not supported. That evidence is CI, which installs vg v1.75.0 and passed on PR #51.

It does not cover

/json and the 3D graph path, whose layout libraries were stubbed. Real subgraph extraction, skipped by design. The PCLAI colouring path, which needs the minigraph walks file this data directory does not contain.

Absolute timings are a developer laptop, not the server. The ratios are the transferable part. Production's own baseline is unchanged and will stay that way until something is promoted to release.

08

Reproducing it

Set S to a scratch directory outside the repo and REPO to the checkout. The full recipe, including the stand-in's source, is in docs/perf/local-endpoint-harness.md.

Build the environment, then run it

S=/tmp/seqtubemap-harness; REPO=$PWD; mkdir -p "$S"/{tools,data,stubs,bin}

python3 -m venv "$S/venv"
"$S/venv/bin/pip" install -r requirements-test.txt uvicorn
git clone --quiet https://github.com/CAST-genomics/panCT.git "$S/tools/panCT"
git -C "$S/tools/panCT" checkout --quiet 03c406b

mkdir -p "$REPO/cache/seqtubemap/mc"
cp "$REPO"/tests/fixtures/seqtubemap/*.gfa "$REPO/cache/seqtubemap/mc/"

GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0=tools.path GIT_CONFIG_VALUE_0="$S/tools" \
GIT_CONFIG_KEY_1=data.path  GIT_CONFIG_VALUE_1="$S/data" \
PYTHONPATH="$S/stubs" VG_SHIM_REPO="$REPO" PATH="$S/bin:$PATH" \
  "$S/venv/bin/uvicorn" main:app --host 127.0.0.1 --port 8100

09

What was left behind

Nothing in the repository. The seeded cache/ directory was deleted, the worktree removed, both uvicorn processes stopped and both ports confirmed closed. git status is clean and origin/release is untouched.

The harness itself — virtualenv, panCT clone, stubs, stand-in, captured documents and server logs — lives in a session scratchpad, which is temporary. Section 08 is what makes it durable.
