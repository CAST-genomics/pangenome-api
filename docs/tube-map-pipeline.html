Two Ways to Draw a Tube Map

A researcher clicks one spot on the pangenome and asks to see inside it. Here is what the server used to do to answer that, what it cost, and what it does instead.

Written 2026-08-28, revised 2026-09-02 when the change went live · every number on this page is measured, and each one says where it was measured

The picture being asked for

The Pangenome Browser draws a whole genome graph in three dimensions. Each vertex of that graph is a node — one stretch of DNA. Click a node and you ask to look inside it: the sequence tube map, a base-by-base picture of how several hundred people's genomes differ across that stretch.

Three words carry the rest of this page. A segment is one small piece of sequence inside the node. A strand is one person's haplotype threaded through those segments — there are typically 464 of them. A band is the atomic thing that gets drawn: one strand crossing one slice of the picture. A single tube map is tens of thousands of bands. (Each of these is pointed at, on a real map, in the illustrated lexicon.)

The server's job is to work out where every band goes, and to get those numbers to the browser. That is the whole assignment. What follows is a story about how far the numbers travelled to get there.

The old way, in one picture

The invisible browser deserves a sentence, because it is the strange part. The drawing code was written to run in a web page, so to run it on the server the server pretends to be a web page: it builds a whole document in memory, lets the drawing code fill it in, and then takes a snapshot of that document as text. Nothing is ever displayed. The document exists only to hold values that were already sitting in memory one step earlier.

The layout computes numbers. A fake browser holds them as text. The wire carries the text. The app parses the text back into numbers.

The browser gives up after 90 seconds, so the bottom row of that table is not a slow feature — it is an absent one. Roughly 43% of catalogued nodes could not be opened at all, and there was no way to tell in advance which ones. The most information-dense regions were exactly the ones nobody could look at.

The failure did not stay put, either. The server was written so that one request had to finish before any other could be served, even though nothing about the work required that. While a 120-second request was in flight, four unrelated requests failed outright — including requests for the 3D graph, a different feature entirely. One person exploring a big region froze everybody else's browser.

Where the 38.9 seconds went

What those 381 lookups are actually reading

The hairline and the bar are not two ends of one file. They are two different files, read two completely different ways, and the distinction is the whole of increment E — so it is worth being exact about which is which.

The two calls inside "finding the region" (main.py:933-934), on the 10,000-base region above.
CallFile it readsHow it reads itCost
SubgraphMC the indexed .gbz — 5.4 GB, plus a 9.3 GB database one query, for the whole region 0.042 s
GenerateWalksMC a .walk.gz — a separate, segment-indexed table of where every assembly sits on every segment one lookup per segment — 381 of them 30.035 s

The pangenome database is not slow and is not implicated. It hands over the segments and links of a 10,000-base region in 42 milliseconds and is not touched again. What it does not hand over is which haplotype goes where — the extracted file has segments and links and no paths at all. Supplying those is the second pass, and it is a different file with a different shape.

The two files, byte for byte

Both halves are small enough to show. This is a real extraction — chr8:78,771,162, 90 bases, nine segments — committed to this repository as a test fixture.

What comes out of the database is sequence and structure, and nothing about people:

What the walk table holds is the missing half, and it is shaped unusually. It is a tabix index — ordinarily a genomic index, chromosome plus start plus end. Here the chromosome column is a constant . and the position column is the segment id. It is a genomic index repurposed as a segment-id index, and fetch(".", id-1, id) means "give me the one row for this one segment".

One row of hprc-v2.0-mc-grch38-v2.2.walk.gz, tab-separated, as _write_walks_mc unpacks it (main.py:340).
ColHoldsExample
1a placeholder chromosome, always the same.
2the segment id — what tabix indexes on181810309
3length of that segment, in bases145
4every haplotype at this segment, comma-separated — each entry assembly|contig:coord:strand HG00544#2|CM089383.1:17162:+,HG00621#1|…:9931:+,… ×464
5repeat placements, or . when there are none.

Column 4 is the whole payload, and it is enormous. One row lists where all 464 haplotypes sit at that one segment. At roughly thirty characters an entry, a single row is on the order of fourteen kilobytes of text — and the loop asks for one row at a time, 381 times.

The loop, step by step

Here is the whole of GenerateWalksMC, in order. Steps 2 through 6 are the body of the loop, and they run once per segment.

1

Open the walk-less GFA and read one line

The file that came out of the database, streamed a line at a time. An L or H line is copied straight through and the loop moves on. An S line is work.

2

Take the segment id out of column 2

181810309. One integer.

3

Seek into the compressed walk file for that one id79 ms, once per segment

fetch(".", id-1, id). Consult the tabix index, seek to the block that holds the row, decompress that block, hand back the row. This step and the next one are the whole 30 seconds, paid 381 times; which of the two carries it is the measurement E is waiting on, below.

4

Tear the row apart in Python

Split on tabs into five columns. Split column 4 on commas into ~464 entries. Split each entry on |, then on :, into assembly, contig, coordinate and strand, and int() the coordinate. Across the region that is roughly 177,000 entries, a field at a time.

5

Accumulate into the coordinate tables

Every entry appends to coord_table[assembly][contig] — three parallel lists holding the interval (coord, coord+length), the segment id, and the strand. Column 5's repeats go into a second table, with a linear scan to reject duplicates already recorded.

6

Copy the S line out unchanged, and go back to step 2

381 times.

7

Only now, write the strands

With the file exhausted: for each assembly and contig, fold the repeats back in, sort the intervals by start, break the run wherever one interval's end is not the next one's start, and emit one W line per unbroken run — W CHM13 0 chr8 79202498 79202786 >181810309>181810311>181810312…. This part is fast, and it is why a crash midway leaves a structurally valid GFA with no paths in it.

381 seeks, to assemble 464 answers, out of a file that was already sorted in the order we wanted to read it.

That is why the cost is flat per segment rather than growing: 65 ms at 13 segments, 65 at 118, 79 at 381. Nothing about the work gets harder as the region grows — there is simply more of the same fixed overhead, paid once per segment. Multiply it out and a 7,000-base region, around 250 segments, spends something like 18 seconds here before a single line is drawn.

Why the lookups can be batched — and in what space

The lookups do not have to be asked one at a time. The table accepts a range, and the segment ids in an extracted subgraph turn out to be all but contiguous.

It is worth being exact about what is contiguous, because the obvious reading is the wrong one. The segments do not tile the genome side by side. A pangenome subgraph is a graph with bubbles: at a variant site, two or more segments occupy the same reference coordinates, and each haplotype takes one of them. In the fixture above, segments 181810310 and 181810311 are a single base each, A and C — the two alleles of one SNP. The finished walks prove it: CHM13 goes >309>311>312 and GRCh38 goes >309>310>312. No strand traverses both, and no arrangement of them into a gapless row of coordinates exists.

What is nearly gapless is the integers. The graph builder assigned segment ids in order along the reference, so extracting a region pulls out an almost unbroken run of them — and an unbroken run of ids is precisely what one range lookup asks for. And the batched form is not hypothetical: the older version-1 path in this same file already groups segment ids into contiguous runs and fetches a run at a time (main.py:231-234 builds the runs, main.py:244 fetches them). What is still unmeasured, and it decides the size of the win. The 65-to-79 milliseconds per segment is not yet split between steps 3 and 4 above: the lookup — seeking and decompressing a block of the file, quite possibly the same block several times over for consecutive segments — and the parsing of 464 haplotypes' coordinates out of the row it returns. If the cost is the lookup, batching is most of the win and it is large. If it is the parsing, batching removes the seeks and the work stays, and E needs a different shape. Timing the two separately over one real region is a short script, but it needs the real walk file and so can only be run on the server. That is the investigation E is waiting on, and it should happen before any number is promised.

What was in the ten megabytes

Every band in the old format carried its strand's colour, its strand's full name, a second copy of that colour, a second copy of its strand's number, and an empty label. Tens of thousands of times. One real 13.6 MB document contained 40,716 empty labels.

Why the big nodes failed at all

Slowness and size are annoyances. The nodes that never loaded were a different problem, and it had a single cause: the invisible document. Measured either side of a render — build the document, then throw it away and see what is released — the answer was unambiguous.

The new way

The change is smaller than the numbers suggest. The layout keeps its numbers instead of handing them to a document; the picture is written out from those numbers; and the same numbers can be requested directly, as numbers.

Three decisions shape the rest:

The numbers are the truth; the picture is made from them

Not two parallel ways of producing an answer — one, with the picture derived from the numbers. Two parallel paths drift apart the moment someone stops watching. One path cannot.

The new format is added, never substituted

The existing address keeps returning exactly what it returned before. Asking for numbers is a request you opt into. The server and the app are separate projects; this way neither has to wait for the other, and the old format stays available as the reference the new one is checked against.

Each strand's details are sent once

A small table at the top of the response lists the ~464 strands with their colours and names. After that, each band carries only where it is and which strand it belongs to. The app copies that block straight onto the screen — there is no reading step to delete, because there is nothing left to read.

How it gets there

Five steps, each shippable on its own, so that a problem with one does not hold up the others. They are lettered in the order they were planned; measurement has since re-ordered what matters.

A

Stop one request from blocking everyoneBuilt

The most severe symptom had a one-line cause: the server was told to handle these requests on the thread that answers everybody. Moving them off it means a slow request is now just a slow request. This fixes the 3D graph too, and it arrived alongside the project's first tests and first automated checks — neither of which existed.

B

Delete the invisible browserBuilt

Collect the layout's numbers directly, and write the picture out from them. Two of the project's five external dependencies existed only to pretend to be a browser and are now gone. Deliberately, the picture came out byte-for-byte compatible with what the app already reads — so this was a server-only change against an unchanged app, and the app itself became the test of whether it worked.

C

Publish the numbersBuilt

Positions became numbers rather than drawing instructions, the strand table moved to the top of the response, and the new format appeared as an option on the existing address. 1.10 MB where the old one is 9.97 MB, measured over the same region rather than projected — better than the 1.5 MB this page predicted. On 2 September 2026 the app read that format off the live server and drew from it, which is the first time anything but a test has. This was the only step that needed both projects to move, and both have.

Writing the app's reader sent three corrections back the other way — three places where the written description of the format and the thing actually being sent had quietly disagreed, each found by a person reading the description rather than the code. That is what the description is for, and it is also why the remaining piece is a test that runs in both projects and fails when they drift apart.

E

Stop looking up 381 pieces one at a timeLargest win left

30 of the 38.9 seconds, in code that costs a flat 79 milliseconds per piece however many pieces there are — the signature of a fixed overhead paid over and over, not of hard work. The pieces are segments, and the lookups are against the .walk.gz table rather than the pangenome database, which answers the whole region in 42 milliseconds and is not implicated. The segment ids being looked up are all but contiguous, and the table takes a range, so the 770 lookups of an 8,000-base region would be two — see What those 381 lookups are actually reading above. It touches nothing the app can see, so it can proceed in parallel with C. What it needs first is a measurement splitting the per-segment cost between the lookup and the parsing, which decides whether batching is most of the win or only part of it.

D

Remove the detour through two extra file formatsCleanup

Two separate programs are launched and two temporary files written, purely to convert between formats we control on both sides — inflating the data thirteenfold on the way. This was originally ranked first, on the reasonable assumption that it was the silliest thing in the pipeline. Measurement put it at 1.6% of a slow request. It is worth doing as a simplification — one fewer tool to install — and it is worth doing last.

The pipeline, format by format

Everything above is the argument. This is the machinery: every representation the data takes between the graph on disk and the pixels on screen, in all three versions of the pipeline — what used to be deployed, what is deployed now, and what D and E are still aiming at. The middle column moved from the right-hand one on 2 September 2026, when the server took C and stopped going back.

Read it down a column and you follow one request. Read it across and you watch representations disappear.

What each hop is actually for

The two GFA files are one extraction split in two, against two different sources. The graph query pulls the segments and links of the requested region out of the indexed .gbz in 0.042 seconds, and that file is then done with. The second pass adds one W line per haplotype, and it reads a separate file — a position-indexed .walk.gz table of where every assembly sits on every node — looking up each segment in it one at a time. That second pass is 30 of the 38.9 seconds, and it is the only stage whose output is cached — which is why a repeated region can come back fast, and why a 1,000-base request once beat a 300-base one.

The .vg and .json pair exists purely to change representation. The subgraph is written out, handed to vg convert to become protobuf, handed back to vg view -j to become JSON, and only then read. The same information costs about 3.9 bytes per segment visit in GFA and about 51 in the JSON — a thirteenfold inflation for a conversion between two formats this project controls both ends of. Increment D does it in process; the golden tests passing with vg uninstalled is how that gets demonstrated rather than claimed.

The emulated document is where the numbers used to go to be turned into text. Increment B replaced it with the collector in seqtubemap/band-data.mjs, which is now the only description of the picture that exists — the document is written out from it by emit-document.mjs, not alongside it. Bands carried curves as path strings there until increment C, which made them six floats — and the picture came out byte-for-byte identical, which is how a change of representation proves it changed nothing else.

The .svg file is written to disk so that it can be opened and streamed back, then deleted by a background task. It is the clearest single example of a stage boundary that used to be a process boundary and no longer is.

Alongside those: memory during a render fell from 1,851 MB to 95 MB; peak memory from 2,446 MB to 473 MB; the fixed cost paid on every request, however small, fell by about 440 milliseconds; and a map that previously exhausted the server's memory limit and produced nothing now renders in 6.4 seconds. All of that is with the format unchanged. C is where the 10 MB becomes 1.10 MB — measured, now, over the same 8,000-base region, and holding between 1.9× smaller at the smallest region and 9.3× at the largest. The ratio is smallest where the response is smallest, because a short region's response is nearly all strand table, and the strand table is the part that does not shrink with the picture.

This is live, as of 2 September 2026. For most of this project's life the sentence here read none of this is live yet — the service was deployed from a separate release branch and everything described above was queued behind it. That queue is gone: the server now runs the same code this page describes, and it is staying there.

So the 120-second and 43%-failure numbers at the top of this page are history. They are what a researcher got, measured on 27 August 2026, and they remain the baseline everything here is read against.

One honest gap. Nobody has yet timed the live service since the change — both times it was looked at, it was looked at rather than measured. The improvements above were all measured off the server, on regions small enough to reproduce there. What the service now does on a large region, in seconds, against a real graph, is the one number this page cannot give you.
